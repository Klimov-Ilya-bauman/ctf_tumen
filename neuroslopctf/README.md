# NeuroslopCTF — исправленная версия

Подробный аудит: [`SECURITY_REPORT_RU.md`](SECURITY_REPORT_RU.md).

## Новый запуск

Требуются Docker и Docker Compose:

```sh
./scripts/setup-env.sh
docker compose up -d --build
```

Сервис: `http://localhost:9090`. Скрипт создаёт `.env` с двумя независимыми
случайными паролями; файл не включается в образ/архив. Не публикуйте `.env`.
Для паролей в `DATABASE_URL` используйте сгенерированные hex-строки либо
корректное URL-кодирование.

Для HTTPS за reverse proxy настройте в `.env`:

```dotenv
PUBLIC_ORIGIN=https://ctf.example.org
COOKIE_SECURE=true
BIND_ADDRESS=127.0.0.1
```

Proxy должен передавать исходный `Host`, ограничивать размер/скорость запросов
и применять собственный per-client rate limit. Приложение намеренно не доверяет
`X-Forwarded-For`; иначе заголовком можно было бы обходить ограничение. При proxy
в контейнере настройте сеть/bind под свою инфраструктуру. Без TLS режим
`COOKIE_SECURE=false` оставлен для локального/CTF HTTP; для публичного production
HTTP небезопасен.

## Обновление существующей установки

1. Сделайте резервную копию БД и тома `/data`; не выполняйте `down -v`.
2. Сохраните прежнее Compose project name, чтобы не подключить пустые тома.
3. Смените скомпрометированные пароли/ключи. Старые DB-пароли автоматически
   **не меняются** от изменения переменных окружения существующего тома.
4. Старый Compose создавал `neuroslopctf` как PostgreSQL superuser. Перед запуском
   новой конфигурации создайте отдельного администратора `postgres` (если его ещё
   нет), задайте ему `POSTGRES_ADMIN_PASSWORD`, задайте пользователю `neuroslopctf`
   новый `POSTGRES_PASSWORD`, затем выполните:

   ```sql
   ALTER ROLE neuroslopctf NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION;
   ```

   Делайте это интерактивно через `psql` с прежним администратором и `\password`,
   не помещая пароли в shell history. Не понижайте единственного администратора,
   пока не проверили вход нового. `scripts/db-init.sh` применяется только к
   **новому** тому, существующую БД он не перенастраивает.
5. Пересоберите образ. Если старый том `/data` принадлежит root, однократно:

   ```sh
   docker compose run --rm --no-deps --user root --cap-add CHOWN \
     --entrypoint sh server -c 'chown -R node:node /data'
   docker compose up -d
   ```

6. Миграция `002_security.sql` выполняется автоматически при старте. Она отзывает
   старые сессии (пользователям нужно войти снова), убирает повторные командные
   покупки подсказок и добавляет ограничения уникальности. Схема меняется:
   перед откатом к старому коду восстановите согласованную резервную копию.
7. Если сервис уже атаковали, исправление кода не восстанавливает достоверность
   данных. Проверьте владельцев, роли, API-токены, приглашения, решения и файлы;
   отзовите подозрительные токены, смените флаги и награды, восстановите данные
   из доверенной копии при необходимости.

## Сборка и проверки без Docker

Node.js 26, pnpm 12.9.1:

```sh
pnpm install --frozen-lockfile
pnpm run build
pnpm test:unit
pnpm --filter @backend/frontend check
pnpm audit
```

Интеграционные тесты требуют PostgreSQL и учётную запись с правами создания
временных БД/ролей. Это **тестовые**, не production credentials:

```sh
TEST_DATABASE_URL='postgres://TEST_ADMIN:TEST_PASSWORD@127.0.0.1:5432/postgres' \
  pnpm test:integration
```

Тест создаёт отдельные случайно именованные БД/роль, запускает сервер с обычной
непривилегированной DB-ролью и удаляет свои ресурсы после выполнения. Указанную
существующую БД он не мигрирует. Без `TEST_DATABASE_URL` интеграционный тест
пропускается явно. `pnpm test` сначала собирает проект и запускает оба набора.

`DATABASE_URL` теперь обязателен для ручного запуска сервера.
